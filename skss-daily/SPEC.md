# SKSS Daily 改造仕様書

- 版：1.2（2026-11-27）
  - 1.1：今日の着地点の分類を複数選択に変更
  - 1.2：種と根を「種・根」1項目にまとめた（実際には同時に行うことが多いため）
- 対象：既存の SKSS Daily
- 実装担当：Claude / Codex
- 目的：創作・事業の成果だけでなく、生活全体の活動負荷と前進を把握し、AIによる進捗分析の精度を上げる。

## 1. 背景と設計原則

現在は「種・根・枝・咲」で前日の活動を記録している。アイデアの詳細はアイデアキャッチャー、思考の深掘りはAIとの対話などで管理しており、日報への再入力は負担になる。一方、家庭業務・通院・各種手続きなどの進捗はメモに埋もれやすく、制作が進まない理由も観測しづらい。

- 花が咲いていない日と、何もしていない日を区別する。
- 日報は詳細なタスク管理やアイデア管理の代替ではなく、活動の観測装置とする。
- 毎朝の入力は原則3分以内。全項目の入力を強制しない。
- 種根枝咲の世界観、既存の配色・書体・カード構成・操作感を維持する。
- 家庭や休養を事業の成果と競わせない。活動量は成績ではない。

## 2. 前日の記録

| 項目 | 定義 | 入力方式 |
|---|---|---|
| 🌱🌳 種・根 | アイデアの発生・収集、調査・壁打ち・方向性の決定・整理 | 未記録／なし／あり／多数 ＋ 任意の詳細 |
| 🌿 枝 | 制作・実務・作業の進展 | 既存の複数項目追加方式 |
| 🌸 咲 | 完成・公開・納品など、明確な成果 | 既存の複数項目追加方式 |
| 🟫 土（新設） | 家庭・健康・生活環境・経理・作業環境など、活動基盤の整備や進展 | 枝・咲と同様の複数項目追加方式 |

### 2.1 種・根の簡略化

- 3段階（なし・あり・多数）の選択を主入力とし、未選択は未記録とする。
- 詳細は任意。既存のテキスト・写真追加機能を削除せず、折りたたみ等でアクセス可能にする。
- 「多数」に厳密な件数基準は設けない。体感で選ぶ。
- アイデアキャッチャーやAI対話の内容を転記する必要はない。外部サービスとの自動連携は今回の対象外。
- 1.2で種と根を1項目「種・根」にまとめた。種だけ・根だけの偏りは今後は区別しない。
- 1.1以前に種・根を別々に記録した日のデータは、消さず・統合せず・補完せず、その日だけ「🌱 種」「🌳 根」として表示・出力・編集できるようにする。

### 2.2 土の追加

例：各種手続きの完了、家族の用事、収納の整理、不用品の出品、通院、経理整理、作業環境の改善、地域や学校関係の役割の一段落。

単に時間を使ったことではなく、片付いたこと・維持できたこと・前進したことを短く記録する。家庭の成果も独立した価値として扱う。既存のタグ追加・削除、写真添付方式を可能な範囲で踏襲する。

## 3. 昨日の活動量（新設）

以下の5領域を独立して体感評価する。

- 🎨 自分の事業・創作（GINsprout、書籍、小説、動画など）
- 💻 バイト・雇用業務
- 🏠 家庭業務・子育て
- 📋 その他の義務（地域・学校関係の役割など）
- 🎮 休養・娯楽

各領域は `0: なし / 1: 少なめ / 2: 普通 / 3: 多め / 4: 非常に多い`。未選択は null（未記録）。ボタン選択式とし、選択解除も可能にする。

実時間ではなく主観的な活動量を記録する。合計値を一定にする必要はない。自動推定や入力の強制はしない。休養の多さを減点しない。

## 4. 今日の咲候補 → 今日の着地点

- ラベル：🎯 今日の着地点
- 説明：今日ここまで進めば十分、という地点をひとつ
- 既存の自由記述欄を維持する。
- 任意の分類：種・根／枝／咲／土／休養（未選択可、複数選択可）※1.1で単一選択から変更、1.2で種と根を統合（以前に選んだ種・根の分類はそのまま表示）
- 例：Servicesページの骨組み完成（枝）、手続きの書類をそろえる（土）、ゲームをして休む（休養）。
- 翌日に達成状況を入力させる機能は今回は必須としない。

## 5. 既存項目の維持

- MF確認済み、マインドマップ確認済みのチェック欄
- 自由記述メモ（分類に入らない気づき・補足・出来事）
- 保存、過去ログ、写真関連機能、GitHub同期、同期状態表示
- 日付・前日記録と当日の目標の対応関係

## 6. 週間集計・過去ログ

現在の今週の咲件数は維持する。過去ログ側に週間集計を追加する。

| 指標 | 集計方法 |
|---|---|
| 種・根 | あり／多数の日数（件数ではない） |
| 枝・咲・土 | 記録項目数 |
| 活動量 | 領域別の体感評価の平均、または合計と記録日数 |

- 種・根の日数と枝・咲・土の件数は単位を明示し、総合スコアに合算しない。
- 活動量は実時間や正確なリソース配分率として表示しない。領域別の棒グラフなどを推奨する。
- 未記録を0として集計しない。記録日数を明示する。データがなければ未記録と表示する。
- 過去ログの日別表示・編集が既存で可能なら、新項目にも対応させる。
- 週の起点・日付処理は既存仕様を維持する。

## 7. AI分析用14日間ログ出力（重要）

既存の「SKSS Daily：直近14日」等のコピー用出力に、新項目を必ず含める。AIが内容と活動負荷を同時に分析できるプレーンテキスト形式とする。

出力例（架空の活動量を含む例示）：

```text
【SKSS Daily：直近14日】
■ 2026-11-26（前日の活動記録）
🌱🌳 種・根：あり（詳細なし）
🌿 枝：なぞいネタ作成／サイト改造続き
🌸 咲：なぞい3話公開
🟫 土：通院／買い物
活動量（0〜4）：事業2／バイト0／家庭3／その他1／休養1
MF確認：未チェック
マインドマップ確認：未チェック
今日の着地点（枝）：Servicesページの骨組み完成
メモ：特になし
```

- 日付の意味（入力日か活動日か）は既存データを確認して明確化する。前日の活動と今日の目標を混同しない。
- 未記録と明示的な「なし」・0は区別する。古いログの項目欠損は「未記録」と出力する。
- 種・根の詳細がある場合は省略しない。
- 既存のコピー操作を維持する。
- 週次集計の追加よりも、この出力への新項目反映を優先する。

### AI分析時の想定観点

- 制作が進まない理由が、家庭・雇用業務・休養・方向性検討のどれに関連するか。
- 種・根に偏り、枝・咲へ移行できていない傾向があるか。
- 制作や成果が継続しているか。生活基盤の整備が進んでいるか。
- 働き方が変わった前後で事業活動の負荷・成果がどう変わったか。
- 記録は主観値であり、因果関係や実稼働時間を断定しない。

## 8. データ互換性・実装上の要件

実際のソースコードは本仕様作成時点では未確認。以下は論理的な追加項目の例であり、既存のデータ形式に合わせて実装すること。

```text
seedRootLevel: null | none | some | many   （1.2〜。詳細は seedRoot: 項目配列）
seedLevel / rootLevel / seed / root: 1.1以前の別々の記録。保持のみ（新規入力欄には出さない）
soil: 既存の枝・咲と同等の項目配列
activityLoad: { creative, employment, household, obligations, rest }
  各値: null | 0 | 1 | 2 | 3 | 4
todayGoalTypes: [] | seedRoot・branch・bloom・soil・rest の組み合わせ（複数選択。[] は未選択。旧データの seed・root も表示する）
  ※1.0初版の単一値 todayGoalType は読み込み時に配列へ変換し、保存時には持たない
```

- 既存の種・根・枝・咲・メモ・目標・写真・チェック項目を保持する。
- 旧データは新項目が欠損していても読み込み・編集・保存できること。欠損を活動なしに変換しない。
- 旧データの種・根の詳細はそのまま表示・出力する。量の評価を勝手に補完しない。
- 既存の目標フィールドは表示名変更を基本とし、データ移行が必要な場合も内容を失わない。
- GitHubへの読込・保存・同期・認証・エラー処理を維持する。既存データの一括上書きや破壊的移行を避ける。
- 未選択、空欄、0、写真のみの項目、旧形式と新形式の混在を扱えるようにする。
- PC・スマートフォンの両方で操作できること。現在のレスポンシブ設計を維持する。
- 家庭・健康等の個人的な情報が含まれ得るため、保存先の公開範囲を確認する。既存リポジトリが公開の場合、個人ログを公開領域へ新たに保存しない。認証情報をコードへ埋め込まない。

## 9. 実装順序

1. 既存ソース、データ構造、同期処理、過去ログ、14日間出力を確認し、変更前のバックアップを確保する。
2. 種・根の簡略化、土、活動量を追加し、保存・読込・旧データ互換を実装する。
3. 14日間出力を更新する。
4. 今日の着地点を実装する。
5. 週間集計・過去ログ表示を拡張する。
6. PC・スマートフォンで動作確認する。

## 11. 今回の対象外・実装担当への注意

アイデアキャッチャーとの自動連携、AI対話の自動取得、タイムトラッキング、総合生産性スコア、通知機能、既存デザインの全面刷新は今回の対象外。

本仕様は設計意図と受入条件を定めるもので、ファイル構成や内部変数名を強制しない。既存実装に矛盾する箇所、プライバシー上の懸念、既存データの破壊を伴う変更があれば、実装前に報告すること。実装後は変更ファイル、変更内容、互換性対応、テスト結果、未対応事項を報告すること。
